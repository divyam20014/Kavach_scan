## TBD-032 evaluation (2026-10-20)

**Method:** the wheels of `filelock` 4.2.4 and `portalocker` 4.4.1 (latest on PyPI at evaluation time) were inspected and exercised from a scratch directory, not installed into the project. Environment: Windows 11, CPython 3.13.5, lock files in the user temp dir (Defender active).

| Check | filelock 4.2.4 | portalocker 4.4.1 |
|---|---|---|
| License / runtime deps | MIT / **none** | BSD-3 / none required (`pywin32` and `redis` are extras) |
| Mutual exclusion: 8 processes × 200 locked read-modify-write increments (expect 1600) | **1600, no lost updates** | 1600, no lost updates |
| Lock blocks a second process while held | yes | yes |
| Lock released by the OS when the holder is killed | yes (re-acquired in 7.8 ms) | yes (3.4 ms) |
| Uncontended acquire+release latency (2000 samples), median / p99 | 3.0 ms / 6.7 ms | 2.4 ms / 4.8 ms |
| Third-party modules loaded by a plain `import` | **none**; `sqlite3` **not** loaded (its RW lock imports lazily) | **`redis`**, `setuptools`, `jaraco`, `more_itertools`, `packaging` (it auto-imports `redis` when present in the environment, as on this machine) |
| Async API for FastAPI | `AsyncFileLock` built in | none |
| API pitfalls seen | — | `timeout` is silently ignored unless `NON_BLOCKING` is set (UserWarning) |

**Why `filelock`:**
1. **Accuracy:** both locked correctly. `filelock` has no implicit dependencies and nothing loaded at import time, which keeps the no-database/no-Redis guarantee checkable.
2. **Performance:** portalocker is about 0.6 ms faster per uncontended lock. That is negligible next to the `fsync` + `os.replace` cost of each atomic write. Contended throughput was equal (about 32–33 s wall time for 1,600 ops, including 8 process start-ups).
3. **Future scalability:** neither library makes the system multi-node; OS file locks are single-host by nature (see `docs/ARCHITECTURE.md` §2.2). Scalability comes from the design instead: per-record lock granularity (no global lock), lock-free readers thanks to atomic replace, and a `storage/locking.py` interface so the backend can be swapped. Any future multi-node backend would itself be a spec change, because Redis and databases are prohibited.

**Phase 01 obligations:**
- Wrap `filelock` in `storage/locking.py`.
- Tune `poll_interval` (the default 50 ms is coarse for contended record locks; start at about 5 ms and measure).
- Benchmark lock + atomic write in a real data dir (`%LOCALAPPDATA%`, which Defender may treat differently from temp).
- Add a test that importing `app` does not load `sqlite3` or `redis`, plus a static guard banning `ReadWriteLock`, `SoftFileLock` and direct `filelock` imports outside `storage/`.
- Add multi-process lost-update and crash-release tests modelled on this evaluation.

**Phase 01 outcome (all obligations done):**
- Wrapper: `backend/app/storage/locking.py`, with `fallback_to_soft=False` (filelock's default `True` would silently degrade to a crash-unsafe soft lock) and `poll_interval=0.005`.
- Banned types and import confinement are enforced by `tests/test_static_guards.py`. `tests/test_startup.py` proves importing the app loads no `sqlite3`/`redis`.
- Throughput measurement (8 threads × 200 locked read-modify-writes, Windows 11 + Defender): filelock alone took **~31 ms/op**, almost all of it threads polling the OS lock against each other; faster polling made it worse (42–49 ms/op). Fix: **two-level locking**, i.e. an in-process mutex per lock path, then the OS lock. Result: **~14 ms/op**, of which ~12.4 ms is the small-file read+write itself; lock overhead ~1.5 ms. Location (`%TEMP%` vs `%LOCALAPPDATA%`) and `preserve_lock_file` made no material difference.
- Single atomic write (temp + fsync + replace) measured at ~4.5 ms on this machine.
- **Verification change:** lock files moved from sidecars to a central `locks/<xx>/<sha256>.lock` directory. Reason: filelock creates missing parent directories, so a sidecar lock taken during a project-delete race could recreate the deleted project's folders. Central locks also keep lock handles out of project directories, so Windows can rename them during deletion.
- Correctness: 1600/1600 thread updates and 60/60 cross-process `update_project` updates with no loss. Crash release and stale lock files are verified (`tests/test_locking.py`).

## Rules for handling TBDs

1. Use safe, conservative defaults when the application can proceed without a decision.
2. Never ask the user to decide every minor implementation detail. Propose a sensible default and record it.
3. A decision that changes safety boundaries, secret handling, data loss risk, externally visible network behavior, or compatibility must be surfaced clearly.
4. Do not mark a decision `DECIDED` merely because code was written. Record the rationale and corresponding tests.
